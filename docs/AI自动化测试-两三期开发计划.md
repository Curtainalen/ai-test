# AI 自动化测试平台两/三期开发计划

> 基于《AI自动化测试.md》方案和当前 `ai-test-platform` 仓库现状整理。
> 建议采用三期交付；资源充足时可将第二、三期合并为两期。

## 1. 结论与范围

### 1.1 总体判断

方案具备落地条件，且仓库已经完成了相当一部分基础建设：认证、项目、需求、接口/UI 资产、异步任务、执行记录、WebSocket、接口执行桥、报告投影和 Agent 受控工具均已有代码或迁移基础。因此后续重点不是重新搭骨架，而是完成以下三件事：

1. 把需求文档变成可确认、可追踪、可作为上下文引用的需求资产。
2. 把接口和 UI 自动化统一成“资产配置 -> AI 候选 -> 人工确认 -> 异步执行 -> 不可变报告”的产品闭环。
3. 把安全、权限、脱敏、执行隔离和可观测性做成平台底座，而不是后补功能。

### 1.2 本计划的产品边界

首个可发布版本包含：

- 项目、成员、环境、权限和全局模型配置。
- PDF/DOC/DOCX/Markdown/TXT 需求导入、解析、版本和需求模块。
- 需求可测性评审、人工确认、需求模块到场景/报告的覆盖追踪。
- OpenAPI/Swagger/Postman/HAR 导入、接口调试、接口场景编排和执行。
- UI 页面/元素资产、受控探索、定位器确认、UI 场景编排和 Playwright 执行。
- RQ + Redis 异步任务、WebSocket 进度、截图/Trace/DOM/请求响应证据。
- 统一报告、失败诊断、看板、AI 调用用量和审计日志。

明确暂不纳入首版：移动端自动化、全量站点无边界扫描、隐式 RAG/知识库召回、Embedding 配置、未经确认的 AI 自动执行。

### 1.3 关键口径决策

附件方案要求移除 pgvector、Embedding 和经验召回；但当前 README/早期文档仍保留旧口径。开发前应以附件方案为准，执行一次“产品口径清理”：删除新流程中的向量检索和 Embedding 配置，保留普通标签、历史报告和显式选择的需求上下文。若业务必须保留经验复用，应作为后续独立期，不得与本计划中的显式上下文规则混用。

## 2. 推荐三期路线

### 第一期：可用闭环 MVP

目标：让一个项目完成“需求/接口资产 -> 人工确认场景 -> 接口执行 -> 报告”的稳定闭环，并为 UI 自动化保留清晰扩展点。

建议周期：6-8 周；团队配置：后端 2、前端 2、测试/产品 1，必要时 DevOps 0.5。

#### 产品交付

- 项目、成员角色、环境、目标地址和基础权限。
- 需求文档上传、异步解析、版本管理、文本/表格/图片内容块和人工校正入口。
- 需求模块人工拆分与确认；先支持文本、表格和原生 PDF/DOCX，OCR 作为受控能力。
- OpenAPI/Swagger 导入、接口列表、模块树、环境变量、全局 Header。
- 共享 RequestComposer：请求方法、URL/path/query/header/body、鉴权、变量和断言。
- 单接口 Preview/Run、接口多步骤场景、变量提取、断言、超时、重试和取消。
- RQ/Redis 执行队列、执行状态、步骤日志、统一脱敏和基础 WebSocket 推送。
- 不可变执行报告：场景版本、环境、请求/响应摘要、断言结果、耗时和错误分类。
- 基础报告列表、失败详情抽屉和需求模块关联。

#### 技术交付

- 统一领域模型和 Alembic 迁移；所有新表保留项目归属、创建者、revision 和审计字段。
- 文档解析器接口统一为 `ContentBlock`，解析任务必须可重试、可取消、可限时。
- 接口执行器只允许访问项目授权环境；写操作默认不重试。
- 密钥不回传、不进日志、不进 LLM 上下文；请求/响应和文件证据统一脱敏。
- 前端优先复用现有接口自动化后端契约和 RequestComposer，不再维护第二套调试语义。

#### 一期验收

- 新建项目后，上传一份需求和一份 OpenAPI，能生成并确认需求模块。
- 用户能基于已确认模块创建接口场景，运行后实时看到步骤状态和最终报告。
- 任务失败时能看到脱敏后的请求、响应、断言和可复现顺序。
- 重启 API/Worker 后，排队、运行、失败、取消状态不产生脏数据或重复报告。
- 空库迁移、旧数据迁移、后端回归、前端构建和一条真实 PostgreSQL E2E 全部通过。

### 第二期：双自动化与 AI 编排

目标：补齐 UI 自动化和 AI 场景编排，使接口/UI 都具备“候选生成、人工确认、隔离执行、证据回放”的完整能力。

建议周期：8-10 周；一期骨架稳定后并行开发。

#### 产品交付

- 多协议 LLM 适配器：OpenAI Chat/Responses、Anthropic、Gemini、Azure、Bedrock 和兼容端点。
- 全局模型配置、连接测试、模型列表、默认配置切换和配置版本追踪。
- AI 需求可测性评审：测试点、前置条件、数据、歧义、风险和建议验收标准。
- AI 接口分组和接口场景编排；生成结果必须是候选版本，支持差异确认和人工编辑。
- UI 目标、起始 URL、域名白名单、页面范围、允许/禁止操作、最大步数等探索边界。
- browser-use 负责规划，Playwright MCP/DOM 证据负责验证，人工确认后沉淀页面、元素和定位器资产。
- UI 场景编辑、步骤确认、隔离 Browser Context 执行、截图、Trace、DOM 快照和步骤日志。
- UI 失败分类、定位器失效建议、人工修复确认和重新执行。
- 需求模块 -> 接口/UI 场景 -> 执行报告的覆盖状态和需求变更影响标记。

#### 技术交付

- LLM 调用统一网关：超时、重试、限流、Token 用量、供应商未返回用量的明确标记。
- Prompt 输入严格限定为用户显式选择的需求模块和授权资产，不读取未选择项目数据。
- UI 探索与正式执行彻底分离；探索器不具备绕过审批直接执行生产性操作的权限。
- actuator 注册、心跳、任务领取、租约、并发槽位和故障回收机制完善。
- Playwright 证据进入对象存储/受控文件目录，报告只保存引用和摘要。
- 需求版本变更时，旧场景标记为待复核，不自动当作有效覆盖。

#### 二期验收

- 同一需求模块可分别生成接口和 UI 候选场景，人工确认后均可执行。
- UI 执行器断线、浏览器崩溃、超时和定位器失败均能回收任务并形成可诊断报告。
- 模型配置切换不会泄露 API Key；历史报告可追溯实际模型配置版本和用量。
- 需求新版本能显示新增/删除/变更模块及受影响场景。

### 第三期：平台化运营与规模化治理

目标：从“能完成一次测试”提升到“可持续回归、可审计运营、可横向扩展”。

建议周期：6-8 周；部分任务可在二期后半段提前启动。

#### 产品交付

- 测试套件、批量任务、定时回归、并发策略、环境矩阵和失败即停策略。
- 项目看板：资产概览、执行趋势、通过率、失败分类、需求覆盖和 AI 用量下钻。
- 报告筛选、CSV/JSON 导出、失败诊断包、截图/Trace/DOM 在线查看和权限控制。
- Agent 受控工具：查资产、生成候选、提交审批、执行、查报告；所有写操作幂等且可审计。
- 测试数据集、敏感字段标记、数据生命周期、租约和失败后的清理策略。
- 管理员操作审计、模型配置审计、执行器管理、配额、限流和项目级资源限制。

#### 技术交付

- 任务幂等键、执行租约、分布式锁、重试边界和重复消息处理。
- 报告与指标从不可变执行事实计算，不从当前可变场景配置计算。
- 结构化日志、Trace ID、Worker/actuator 健康检查、队列积压监控和告警。
- 数据库备份恢复、文件留存策略、密钥轮换、环境白名单和 SSRF 防护。
- 负载测试：并发任务、WebSocket 连接、报告查询、文件上传和 LLM 限流。

#### 三期验收

- 可配置每日/每次发布回归，任务和报告可追溯、可重跑、可取消。
- 看板所有统计均可下钻到报告和失败步骤。
- Agent 无法绕过权限、审批、环境白名单和脱敏边界。
- 在目标并发下队列、执行器、数据库和 WebSocket 保持稳定，异常后能自动恢复或明确失败。

## 3. 两期压缩方案

如果必须两期完成，建议这样合并：

| 期次 | 合并范围 | 发布标准 |
|---|---|---|
| 第一期（10-12 周） | 三期第一期全部内容 + 二期接口 AI 编排 + 基础模型配置 + 基础 UI 资产/执行 | 接口闭环稳定，UI 能完成一条受控主流程，需求覆盖可追踪 |
| 第二期（8-10 周） | 二期剩余 UI 智能探索/诊断 + 三期全部平台化能力 | 双自动化可持续回归，报告/看板/Agent/治理达到生产可用 |

两期方案的主要风险是 UI 探索器、LLM 适配、接口编排和平台治理同时进入第一期，集成测试压力会明显增大。若团队少于 5 名全职研发，建议坚持三期。

## 4. 建议的工作包拆分

1. 基线与口径清理：确认移除 Embedding，整理 README/旧文档/环境变量/迁移策略。
2. 需求资产：文件安全、解析器、内容块、版本差异、模块确认、评审任务。
3. 接口资产与执行：导入、RequestComposer、变量/断言、执行队列、报告。
4. AI 网关：协议适配、配置版本、Token 用量、脱敏和 Prompt 上下文边界。
5. UI 资产与 actuator：探索边界、页面/元素/定位器、隔离执行、证据采集。
6. 覆盖与报告：需求关联、变更影响、报告详情、看板事实口径。
7. 套件与治理：批量回归、数据集、Agent 审批、审计、配额和可观测性。
8. 交付验证：契约测试、单元测试、PostgreSQL/Redis E2E、浏览器 E2E、迁移演练、容器验收。

每个工作包都必须同时交付后端 API、前端页面、权限/脱敏、数据库迁移、测试和验收数据，避免只完成页面或只完成接口。

## 5. 非功能底线

- 所有 AI 结果都是候选结果，未经人工确认不得进入正式执行。
- 所有执行目标必须经过项目环境白名单校验，禁止任意 URL 访问和 SSRF。
- 所有密钥、Token、Cookie、密码、个人信息、文件内容和响应敏感字段必须统一脱敏。
- 报告不可被后续场景编辑覆盖；场景、需求、模型配置和执行器均需保留版本信息。
- 写操作默认不自动重试；取消必须是协作式，且最终状态只能落到明确终态。
- 解析、探索、执行和 LLM 调用都必须有限时、可观测、可审计。
- API、数据库迁移和 WebSocket 契约需要向已有客户端兼容，废弃能力先标记再移除。

## 6. 启动前需要冻结的决策

1. 最终采用两期还是三期；建议三期。
2. 是否完全移除 RAG/Embedding；按附件方案建议“是”。
3. 首期支持的 OCR 引擎、对象存储方式和单文件/单任务上限。
4. 首期支持的 LLM 供应商及是否允许自定义兼容端点。
5. UI 首期覆盖的浏览器、认证方式、允许操作和测试环境。
6. 生产并发目标、数据留存周期、审计留存周期和备份恢复目标。
7. 是否允许 Agent 进入首版；建议首版仅保留受控 API 和审批模型，完整 Agent 放第三期。

## 7. 推荐首个迭代顺序

先完成口径冻结和现状基线，再按“需求资产最小闭环 -> 接口执行闭环 -> 统一报告 -> AI 编排 -> UI 执行 -> 看板治理”推进。每个迭代结束都用一条真实业务链路验收：上传文档，确认需求模块，导入接口或配置 UI，确认场景，执行任务，查看脱敏报告并回到需求覆盖。
