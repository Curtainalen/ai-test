# 需求模块拆分修改方案

## 1. 目标

在现有需求文档上传和解析能力的基础上，完善以下闭环：

```text
文档解析完成
  -> 生成需求模块候选
  -> 用户查看和编辑模块
  -> 用户新增、拆分、合并或排序模块
  -> 用户确认模块
  -> 模块进入需求评审和测试生成流程
```

前端不再把“文档正文”作为主要展示区域，而是直接以需求模块为核心。数据库中的 `ContentBlock` 继续保留，用于模块来源追溯、版本比较和审计，但不在需求详情页默认展示。

本方案明确不引入 RAG、Embedding、向量数据库或隐式知识召回。AI 只能使用用户显式选择的当前需求文档版本和需求模块。

## 2. 当前基础能力

当前项目已经具备以下基础：

- PDF、DOCX、Markdown、TXT 文件上传；
- 异步文档解析任务；
- 文本、标题、列表、代码块、表格等 `ContentBlock`；
- DOCX 图片解析基础；
- 文档版本和解析状态；
- `RequirementModule` 需求模块；
- 模块来源 `source_block_ids`；
- 模块确认和需求覆盖基础；
- 需求评审服务基础。

相关文件：

- `backend/app/models/assets.py`
- `backend/app/services/documents.py`
- `backend/app/services/requirement_assets.py`
- `backend/app/services/requirement_reviews.py`
- `backend/app/worker_jobs.py`
- `frontend/src/pages/RequirementsPage.tsx`

## 3. 数据结构

保留以下数据关系：

```text
RequirementDocument
  -> DocumentVersion
      -> ContentBlock
          -> RequirementModule
```

### 3.1 ContentBlock

`ContentBlock` 是原始文档事实层，继续保存：

- 文本、标题、列表、表格和图片内容；
- 内容顺序；
- 页码或段落位置；
- 原始解析定位信息；
- 解析置信度；
- 是否需要人工校正。

它不作为前端需求详情页的主要展示对象。

### 3.2 RequirementModule

现有字段继续保留：

- `id`
- `project_id`
- `document_version_id`
- `name`
- `description`
- `source_block_ids`
- `status`
- `revision`
- `confirmed_by`
- `confirmed_at`

建议补充：

- `order`：模块顺序；
- `parent_module_id`：父子模块关系；
- `split_method`：`heading / rule / ai / manual`；
- `confidence`：AI 拆分置信度；
- `created_by`、`updated_by`；
- `archived_at`。

如果当前阶段需要控制范围，至少先增加 `order` 和 `split_method`。

## 4. 模块状态

建议使用以下状态：

```text
pending_confirmation  待确认
confirmed              已确认
changed                已修改，需重新确认
needs_review           因新版本或关联内容变化，需要复核
archived               已归档
```

状态流转：

```text
AI/规则生成
  -> pending_confirmation
  -> 用户编辑
  -> changed
  -> 用户确认
  -> confirmed
```

新版本上传后，旧的已确认模块标记为 `needs_review`。已经被测试场景引用的模块不能直接物理删除，应改为 `archived`。

## 5. 后端接口

主要业务逻辑位于 `backend/app/services/requirement_assets.py`，接口位于 `backend/app/api/assets.py`。

### 5.1 获取文档详情

```http
GET /api/projects/{project_id}/requirements/{document_id}
```

默认返回：

- 文档基本信息；
- 版本列表；
- 当前版本解析状态；
- 需求模块列表。

不需要默认返回 `blocks`。如有调试或定位需要，可以提供独立的受控接口：

```http
GET /api/projects/{project_id}/requirements/{document_id}/blocks
```

### 5.2 生成模块候选

```http
POST /api/projects/{project_id}/requirements/{document_id}/split
```

请求示例：

```json
{
  "method": "auto",
  "heading_level": 2,
  "include_context": true
}
```

支持：

- `heading`：按标题拆分；
- `rule`：按编号、段落和固定结构拆分；
- `ai`：由大模型识别模块；
- `manual`：完全由用户手工建立模块。

生成结果必须是 `pending_confirmation`，不能直接成为正式模块。

### 5.3 模块操作

```http
POST   /api/projects/{project_id}/requirement-modules
PATCH  /api/projects/{project_id}/requirement-modules/{module_id}
DELETE /api/projects/{project_id}/requirement-modules/{module_id}
POST   /api/projects/{project_id}/requirement-modules/{module_id}/confirm
POST   /api/projects/{project_id}/requirements/{document_id}/confirm-modules
POST   /api/projects/{project_id}/requirement-modules/{module_id}/split
POST   /api/projects/{project_id}/requirement-modules/merge
```

模块确认前检查：

- 模块名称不能为空；
- 来源内容块必须属于当前文档版本；
- 模块必须存在来源，或明确标记为人工创建；
- 当前 revision 必须匹配，避免并发覆盖。

编辑已确认模块时，应将状态改为 `changed`，并让关联评审、测试点和覆盖关系进入复核状态。

## 6. 模块拆分算法

采用三层策略。

### 6.1 标题拆分

优先识别 Markdown 和 DOCX 标题层级：

```text
# 用户管理
## 用户登录
## 用户注册
## 密码重置
```

生成“用户登录”“用户注册”“密码重置”等模块。

### 6.2 规则拆分

无清晰标题时，根据以下特征识别边界：

- `1.1`、`2.3` 等章节编号；
- `REQ-LOGIN-001` 等需求编号；
- 连续空行；
- 表格中的功能分组；
- “功能说明”“异常处理”“权限要求”等固定结构。

### 6.3 AI 拆分

确定性规则无法有效拆分时，才调用 LLM。输入只包含当前文档版本的明确内容，输出结构化 JSON：

```json
{
  "modules": [
    {
      "name": "用户登录",
      "description": "用户通过账号和密码登录",
      "source_block_sequences": [4, 5, 6],
      "confidence": 0.92
    }
  ]
}
```

AI 不得读取其他文档、知识库或项目数据，也不得补充原文中不存在的业务规则。AI 返回非法 JSON 或调用失败时，应回退到规则拆分或让用户手工处理。

## 7. 异步任务

当前解析任务位于 `backend/app/worker_jobs.py`。建议保持以下阶段：

```text
读取文件
  -> 解析内容
  -> 保存 ContentBlock
  -> 生成模块候选
  -> 更新解析状态
```

进度可以细分为：

```text
0%   任务开始
20%  文件读取
50%  内容解析
70%  内容块保存
85%  模块拆分
100% 模块候选生成
```

模块拆分失败不应删除已成功解析的内容块。应保留解析结果，并允许用户点击“重新拆分”。

## 8. 前端界面

重点修改 `frontend/src/pages/RequirementsPage.tsx`。

页面结构改为：

```text
需求文档详情
  -> 文档名称、版本、解析状态
  -> 需求模块操作栏
  -> 需求模块列表
  -> 模块编辑区域
  -> 模块确认区域
```

移除或隐藏：

- “文档正文”全文展示；
- 内容块列表展示；
- 以正文为中心的编辑入口。

模块列表展示：

- 模块名称；
- 模块说明；
- 模块状态；
- 来源页码或段落；
- 关联测试点数量；
- 覆盖状态；
- 编辑、拆分、合并、确认等操作。

页面状态：

```text
解析中：显示解析进度
解析完成但没有模块：显示“AI 拆分”和“手工新增”
模块待确认：显示模块列表和“确认全部模块”
模块全部确认：显示“开始 AI 需求评审”
```

## 9. AI 需求评审衔接

模块确认后，评审输入只能是：

```text
当前文档版本
  + 用户确认的需求模块
```

评审输出包括：

- 测试点；
- 前置条件；
- 测试数据；
- 正常、异常和边界流程；
- 权限和安全风险；
- 需求歧义；
- 缺失验收标准；
- 可测性评分和改进建议。

AI 输出应先保存为候选，经过人工确认后才能成为正式测试点。

## 10. 与测试场景关联

目标关系：

```text
需求模块
  -> 需求测试点
      -> API/UI 测试场景
          -> 执行报告
```

场景和报告需要保存：

- 需求模块 ID；
- 需求测试点 ID；
- 文档版本 ID；
- 模块 revision；
- 执行时需求快照。

需求模块发生变化后，关联场景应变为 `needs_review`，不能继续默认作为有效覆盖。

## 11. 版本变化处理

当前系统已经支持文档版本和新版本上传，但还需要补充实际的需求 Diff。

目标流程：

```text
上传 v2
  -> 解析 v2
  -> v1/v2 模块匹配
  -> 标记新增、删除、修改模块
  -> 关联场景标记 needs_review
  -> 页面显示差异
```

建议比较：

- 模块新增；
- 模块删除；
- 模块标题变化；
- 模块正文变化；
- 验收条件变化。

该功能可以放在需求模块闭环完成后实现，不阻塞第一阶段模块拆分。

## 12. 开发顺序

### 阶段 1：移除正文展示

- 修改需求详情页布局；
- 以模块列表作为主视图；
- 保留版本选择器；
- 保留后端 `ContentBlock` 数据。

### 阶段 2：完善模块拆分

- 实现标题拆分；
- 实现规则拆分；
- 增加模块顺序；
- 关联来源内容块；
- 增加 AI 拆分和失败回退。

### 阶段 3：完成模块编辑和确认

- 新增、编辑、拆分、合并；
- 排序和批量确认；
- 状态流转；
- revision 冲突处理；
- 操作审计。

### 阶段 4：接入需求评审

- 只读取已确认模块；
- 生成测试点候选；
- 人工确认测试点；
- 模块变更后让旧评审失效。

### 阶段 5：接入测试场景

- 场景引用需求模块；
- 测试点关联 API/UI 场景；
- 执行报告保存需求快照；
- 需求变更后场景进入 `needs_review`。

### 阶段 6：实现版本差异比对

- 新旧模块匹配；
- 模块级差异计算；
- 差异页面；
- 受影响场景列表；
- 复核确认流程。

## 13. 第一阶段验收标准

1. 上传 Markdown/DOCX 后能够完成解析。
2. 解析完成后能够生成需求模块候选。
3. 页面不显示“文档正文”版块。
4. 页面直接展示需求模块。
5. 用户可以编辑模块。
6. 用户可以新增和删除待确认模块。
7. 用户可以确认模块。
8. 模块能够追溯到原始 `ContentBlock`。
9. 模块确认后才能进入需求评审。
10. 全流程不依赖 RAG、Embedding 或知识库。
