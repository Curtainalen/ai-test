# 需求模块完善计划

## 目标

把需求文档模块补到「能当接口 / UI 自动化的上游资产」，然后立刻回到 UI 主攻。

完成后用户应能走通：

```text
上传需求 → 看到文档和正文 → 校正模块边界并确认
  → AI 基于模块正文产出测试点 → 人工批准
  → 接口 / UI 按模块名和测试点标题选择上下文
```

语义以 `docs/AI自动化测试.md` 为准：模块确认后才能评审；评审产出测试点；下游只吃用户显式选中的已确认模块 / 已批准测试点；不使用 RAG。体验只借鉴 WHartTest 的工作台（列表、看正文、改模块、确认后再 AI），不照搬六维质量报告、问题清单和知识库召回。

## 不可变边界

- 不新建表、不新队列。继续使用现有 `RequirementDocument`、`DocumentVersion`、`ContentBlock`、`RequirementModule`、`RequirementReview`、`RequirementTestPoint`、`RequirementCoverage`。
- AI 结果只作为候选；未经人工确认不得被接口分组、场景编排或覆盖追踪引用。
- 评审 Prompt 只能包含当前模块名称、说明及其 `source_block_ids` 对应内容块，不读取其他文档、未选模块或项目外资产。
- 不引入 OCR、DOC 容器转换、Embedding、向量检索或第二套文档模型。
- 不破坏一期接口自动化契约；第三刀对 UI 页只改测试点数据源，不改探索 / 执行主流程。
- 当前未提交的 UI 探索改动先保留；本计划尽量只动需求相关文件。

## 三刀顺序

必须按刀推进，做完一刀再开下一刀。每刀只有在后端、前端和对应测试均通过后才能勾选。

- [x] 第一刀：文档工作台
- [x] 第二刀：模块带着正文被确认
- [x] 第三刀：评审吃正文，下游能选

三刀完成后切回 UI 自动化；覆盖看板、版本可视化 diff、OCR 不在本计划内。

## 阶段完成规则

每刀结束时必须同时满足：

1. 相关后端单测和 `RequirementsPage` 测试通过。
2. 用 `examples/requirements/user-login.md` 手工走通该刀验收项。
3. 本文件对应刀标记为完成。

## 第一刀：文档工作台

### 目标

需求页刷新后仍能找回文档，并能看见解析出的正文。页面从一次性上传变成可继续使用的资产工作台。

### 后端

- 新增 `GET /projects/{project_id}/requirements`：返回文档列表（标题、最新版本号、解析状态、文件名、上传时间）。
- `GET /projects/{project_id}/requirements/{document_id}` 增加可选 `version_id`；默认仍取最新版。
- 新增 `PATCH /projects/{project_id}/content-blocks/{block_id}`：只改正文和 `needs_correction`，不改 `seq` / `source_locator`。
- 上传继续使用现有 `POST /projects/{project_id}/requirements/upload`；前端开始传入已有 `document_id` 以创建新版本。

### 前端

- 左侧文档列表，选中后加载详情。
- 版本下拉；解析中每 3 秒轮询，直到 `completed` / `failed` / `canceled`。
- 展示 `ContentBlock`：类型、正文、来源定位（页码 / 段落 / 行号）、置信度、`needs_correction`。
- 低置信度块允许改正文；保存后清除待校正标记。

### 主要文件

- `backend/app/services/requirement_assets.py`
- `backend/app/api/assets.py`
- `backend/app/schemas/assets.py`
- `frontend/src/pages/RequirementsPage.tsx`
- `frontend/src/pages/RequirementsPage.test.tsx`
- `backend/tests/test_requirement_modules.py`（或新增文档列表测试）
- `docs/contracts.md`（补列表与内容块接口）

### 验收

- 上传示例 Markdown，刷新页面后文档仍在列表中。
- 解析完成后能看到「用户登录 / 正常登录 / 安全要求」标题、段落和表格。
- 低置信度块可改，改正后 `needs_correction` 消失。
- 可切换历史版本查看对应内容块和模块。

## 第二刀：模块带着正文被确认

### 目标

「确认模块」变成看过正文、改过边界之后的动作，而不是对着空表点按钮。

### 后端

- 修改 `suggest_modules`：每个标题吃到下一个同级或更高级标题之前的全部 block；`description` 用后续段落摘要填充。无标题文档仍整篇一个模块。
- 新增 `POST /projects/{project_id}/requirement-modules`：手工新增模块。
- 新增 `DELETE /projects/{project_id}/requirement-modules/{module_id}`：仅 `pending_confirmation` 可删。
- 现有 `PATCH` / `confirm` 规则保持不变：
  - 确认前必须关联至少一个来源块。
  - 已确认模块被编辑 → `changed`，覆盖标 `NEEDS_REVIEW`，旧评审 `superseded`。
  - 已确认或已评审模块不能直接删除。

### 前端

- 模块表展示名称、状态、来源块数和正文预览。
- 点选模块后，内容区高亮其来源块，可勾选增删来源。
- 可改名称和说明，保存后再确认。
- 仅 `confirmed` 允许发起 AI 评审；`changed` / `needs_review` 必须重新确认。

### 主要文件

- `backend/app/services/documents.py`
- `backend/app/services/requirement_assets.py`
- `backend/app/api/assets.py`
- `backend/app/worker_jobs.py`（若拆分结果写入逻辑需对齐）
- `frontend/src/pages/RequirementsPage.tsx`
- `backend/tests/test_requirement_modules.py`

### 验收

- 示例 Markdown 能拆出带正文的「正常登录」「安全要求」，而不是只有标题块。
- 用户能把相邻段落划进同一模块后确认。
- 改已确认模块后，旧评审和覆盖进入待复核，不能继续当有效上下文。
- 无来源块的模块不能确认。

## 第三刀：评审吃正文，下游能选

### 目标

需求模块开始为接口场景和 UI 探索提供真正的业务上下文。

### 后端

- 评审 Worker 按 `source_block_ids` 取出内容块，Prompt 只带：模块名称、说明、块类型、正文、来源定位。
- 正文合计设上限（约 20k 字符）；超限返回明确错误，不得静默截断后假装评审完整。
- 列表接口补可读名称，不再只返回 UUID：

| 接口 | 增加字段 |
|---|---|
| `GET /ai/requirement-reviews` | `module_name`、`module_status` |
| `GET /ai/requirement-coverages` | 测试点标题、模块名、场景名 |
| `GET /ai/requirement-test-points` | `module_id`、`module_name` |

### 前端

- 评审表、覆盖表用模块名和测试点标题展示。
- 需求页可从评审跳回对应模块。
- UI 探索和接口场景候选改为请求 `GET /ai/requirement-test-points`，按模块分组。
- 未批准测试点不得出现在下游选择器。

### 主要文件

- `backend/app/ai_worker_jobs.py`
- `backend/app/services/requirement_reviews.py`
- `frontend/src/pages/RequirementsPage.tsx`
- `frontend/src/pages/UiAutomationPage.tsx`（仅测试点数据源）
- `frontend/src/components/ScenarioWorkspace.tsx`（仅测试点数据源）
- 对应前后端测试

### 验收

- 对带正文的「正常登录」做评审，测试点能对上正确密码 / 错误密码路径，而不是只根据模块名编造。
- 接口场景和 UI 探索下拉显示 `正常登录 · 正确用户名与密码` 这类标题。
- 单测断言评审 Prompt 不含未关联内容块。
- 未批准测试点不会出现在下游选择器。

## 本计划不做

| 项 | 原因 |
|---|---|
| OCR / 扫描件自动识别 | 一期已冻结；低质量块继续人工校正 |
| DOC 转换 | 继续提示导出为 DOCX 或 PDF |
| 加密 PDF 解析密码 | 非「能当上下文」的门槛 |
| 版本可视化 diff | 后端已把旧模块和关联场景标为待复核 |
| AI 自动拆模块 | 启发式带正文 + 人工改边界足够 |
| 六维质量评分和问题清单 | WHartTest 的评审哲学，不是本平台测试点模型 |
| 知识库 / Embedding / RAG | 规格禁止隐式检索 |
| 需求覆盖看板 | 依赖接口 / UI 执行事实，等主路径跑通后再做 |
| 新表或新队列 | 现有模型和 RQ 解析任务足够 |

## 三刀之后

需求模块对当前产品的职责到此齐备：产出可确认模块和已批准测试点。随后主攻回到 UI 自动化（受控探索、定位器、隔离执行、证据）。覆盖状态看板放到 UI 主路径能产出报告之后再做。
